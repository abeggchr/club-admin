# Email goes through ePost by default; SMTP is the fallback for hosts that allow it

The club sends Invoices by email and by post. The app is deployed on Railway, which blocks outbound SMTP (ports 25, 465 and 587) on its Free, Trial and Hobby plans; there the test email and every invoice email fail with "The operation has timed out". The ePost account that already sends letters can send email as well, over HTTPS, so one ePost API key now covers both.

- **One Email channel, two backends.** The Delivery Channel stays `Email`. If the SMTP group is set, the app sends through SMTP. Otherwise, if an ePost API key is stored, it sends through ePost. With neither, email is not configured. SMTP is therefore optional, meant for anyone hosting on a platform that allows outbound SMTP. `EmailBackends.Resolve` is the single place that decides; the Settings response reports the result as `emailBackend` so the UI never repeats the rule.
- **No fallback on failure.** If SMTP is set but the send fails, the treasurer sees the error. The app does not retry through ePost: that would bill the club for a delivery nobody chose.
- **The club's address is a club setting.** `FromAddress` moved from the SMTP group to the "Klub" section, and the column was renamed (`SmtpFromAddress` to `FromAddress`). It is the `From` of SMTP mails and the `Reply-To` of ePost mails. It is required once an SMTP group is set, and email is not configured without it, whichever backend is used.
- **ePost mails never set a sender.** ePost sends from `noreply@epost.ch`; the club only appears as Reply-To (and in the display name), so replies reach the club. When `emailAdditionalInfo.sender` was set to the club's address in the proof of concept, ePost signed the mail as the club's domain (DKIM selector `sec-epost`) without the key being in DNS, and SPF failed too. With `p=reject` on the domain, DMARC failed and the mail went to spam; a free-mail address could never pass. Sending as the club's own domain would need ePost's DKIM and SPF records in the club's DNS. That is possible later as an opt-in setting, off by default, because most treasurers cannot edit DNS and a half-done setup silently lands in spam.
- **The PDF arrives as an attachment**, as with SMTP. The Sent Remark names the way: "per Email" for SMTP, "per Email (ePost, <id>)" for ePost.
- **It costs money.** ePost bills every delivery; in the proof of concept (25 Nov 2026) one email cost 6 Rappen. The price is not hard-coded anywhere in the app; the Settings page, the send dialog and the bulk-send dialog only say that an ePost email is billed. With ePost as the email backend, the bulk send prefers email over a letter for people with an email address, which is also the cheaper way.
- **The test email stays SMTP-only.** "Test-E-Mail senden" tries the unsaved SMTP form and the club address. It never goes through ePost, so clicking it costs nothing.
- **Development and tests never call ePost.** `InMemoryEPostHandler` answers both letters and emails and records the metadata it received.
